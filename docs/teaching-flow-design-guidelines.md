# 讲题流程设计规范

本规范用于 Math Motion Lab 后续新增题目。核心原则是：先设计讲题体验，确认后再开发代码。

## 强制工作流程

以后新增任何题目，都按下面顺序执行：

1. 先理解题目、目标年级、讲解重点和可修改参数。
2. 不直接写代码。
3. 读取 `DESIGN.md` 和 `docs/scene-led-teaching-reference.md`，检查已有课程和 `design-skill/` 中是否有适合的视觉或交互参考。
4. 先输出 `Design Read`，说明参考什么、借用什么、改变什么、明确不照搬什么。
5. 再输出“效果设计方案”，说明页面如何讲、每一步点击后出现什么、哪些数字是动态生成的。
6. 等用户确认设计方案。
7. 用户确认后，才开始写 HTML、CSS、JS 和测试。

如果用户只给出一道新题目，默认任务是“先设计效果”，不是“直接开发页面”。

## 设计参考发现

新题不是默认从零设计。Agent 必须按下面顺序寻找依据：

1. 项目 `DESIGN.md`：决定全站视觉语言和公共课堂外壳。
2. 已有相似课程：复用已经验证过的布局、控件和讲题节奏。
3. `.agents/skills/build-bilingual-math-lesson/references/design-resource-map.md`：按题型、年龄和视觉需求选择本地设计参考。
4. 用户提供的截图、网址、品牌或风格描述。

每次新建或视觉重做课程时，先给出：

```text
Design Read

页面类型：
老师和学生：
目标年级与教学任务：
视觉气质：
信息密度：低 / 中 / 高
动效强度：低 / 中 / 高
基础视觉参考：
交互参考（可选）：
Keep：保留哪些可复用特征
Adapt：哪些内容需要改成数学课堂表达
Avoid：哪些品牌特征、装饰或交互明确不用
题目专属视觉：用什么画面让数学关系被看见
```

最多选择一个基础视觉参考和一个交互参考。参考的是层级、节奏、色彩角色、材质和交互反馈，不照抄品牌、吉祥物、专有字体、整页布局或产品文案。没有合适参考时也要写明原因。

## 讲题页的定位

讲题页不是计算器，也不是直接给答案的结果页。默认形态是老师控制的单舞台课件：老师负责提问、停顿和讲解，页面负责把老师刚刚说到的数学关系变成可见动作。

默认布局只有三个层级：

```text
课程标题与低强调工具
当前提问 + 单一持久数学舞台
上一步 + 简洁进度 + 下一步
```

数学舞台占据主要教学面积，不再默认设置常驻讲解侧栏。参数、语言、全屏等工具放在页头、弹窗或抽屉中；只有参数必须持续参与推理时，才允许增加低强调控制区。

老师可以点击舞台空白处、“下一步”按钮或键盘推进。每次操作只执行一个数学增量，动作结束后必须停住，等待老师继续提问或解释。页面不自动播放，不代替老师朗读，不把时间轴当成视频。

同一界面不等于主体画面没有变化。点击后应当让当前讲解涉及的对象新增、移动、分组、替换、比较、标注或检验；不变对象必须留在原位。

### 默认模式的七条判断

1. **一个舞台：**主要推理发生在同一组数学对象上。
2. **一次一动：**一次点击只完成一个能用一句话说清的数学变化。
3. **动作后停：**动画结束即进入等待状态，不自动跳到下一步。
4. **先看后命名：**先让学生看见变化，再出现对应数字、词语或算式。
5. **焦点唯一：**一个时刻只允许一个主要观察目标。
6. **外壳克制：**导航和工具能用即可，不通过装饰争夺注意力。
7. **最后作答：**推理与检验完成后，最终一步才显示完整答案。

以后设计新题目时，先写出这道题的“持久对象”和“可见动作链”。如果无法说明每次点击究竟发生了什么数学变化，就还没有完成课件设计。

## 讲师同步的场景推进合同

讲题页的目标不是“每一步换一张信息卡”，而是让讲师的话在一个稳定数学场景中变成可见动作。新建或视觉重做课程时，必须遵守 `docs/scene-led-teaching-reference.md`：

1. 先确定贯穿主要推理的数学对象和固定场景。
2. 每次点击只执行一个可解释的数学增量，例如增加、移动、分组、替换、比较或检验。
3. 先让视觉动作发生，再出现命名该动作的数字、词语或算式。
4. 相邻步骤中的不变对象保持位置、尺寸、颜色和绘制语法稳定。
5. 不用头像卡片、柱状条、对比卡和结果卡反复替换同一数量关系；必须换表示法时，要设计清楚的视觉过渡。
6. 讲稿按“提问—停顿—动作—命名—连接”同步到每一个教学停靠点。

开发前的方案必须增加 `Persistent Scene`、`State Delta Map`、`Narration Sync`、`Representation Change`、`Motion Meaning` 和 `Reduced Motion` 六项。缺少任何一项时，不进入编码。

默认交互顺序为：

```text
老师提问
→ 学生观察并回答
→ 老师点击
→ 一个数学动作发生
→ 数字或算式命名这个动作
→ 页面停住，老师连接画面与结论
```

## 第一步开场页硬性规则

第一步必须是独立的“读题/认识题目”开场页，不能直接进入规律观察、计算方法、图形变换或某一个局部条件。开场页必须在讲题舞台内同时呈现：

1. 题目的情境和对象。
2. 全部已知条件、数字、单位和动作方向。
3. 最终要解决的问题。
4. 一个让学生复述“知道什么、要找什么”的开场提问。

常驻在页头的“当前题目摘要”只用于翻页后的持续提醒，不能代替开场页。标题、进度标签、参数面板或演讲稿中出现完整题目，也不能代替讲题舞台里的完整介绍。开场页不讲方法、不列局部推导公式、不默认学生已经知道题意；第二步以后才能进入分析和讲解。

完整题目必须由当前参数动态生成。参数改变后，开场页也必须同步更新，并回到第一步。

## 答案显示规则

不能一打开页面就显示最终答案。

推荐节奏：

1. 前面先出题、提问、分析已知条件。
2. 中间逐步尝试方案或推导公式。
3. 后半段才出现候选方案比较。
4. 最后一步才显示完整答案。

任何辅助区域也不能提前显示“当前答案”“最优方案表”。如果需要说明，只显示当前步骤的讲解提示和当前板书。

## 面向小学生的“讲透”工作流

小学讲题不能用更高级的术语压缩推理。设计讲解前，先确认目标年级已经学过什么、还没有学过什么，再决定页面语言和证明方式。

每道新题按下面顺序设计：

1. **确定认知边界：**列出学生已经掌握的运算、图形和单位；学生尚未学习的因数、字母代数、根号或专业术语，不直接出现在学生页面。
2. **找到真正卡点：**不要只写计算步骤，要说明孩子最可能在哪一步不理解，例如“为什么只看个位”“为什么形状变了面积没变”。
3. **先给可观察证据：**使用实物式画面、连续例子、反例、拆分或重新排列，让学生先看见规律；不能用一句公式代替关键推理。
4. **一句一问地推进：**每页只问一个问题，先让学生猜或观察，再揭示当前结论；关键结论必须能从本页画面和算式直接得到。
5. **证明答案而不只算出答案：**不仅说明某个结果可行，还要解释为什么成立、为什么没有漏掉更合适的结果，以及单位为什么这样写。
6. **主问题讲完再反向验证：**可以从答案倒推原始条件，或把答案代回题目检查；反向验证要强化当前知识，不另开一条更复杂的解法。
7. **最后才做适度拓展：**拓展用于总结规律、缩小尝试范围或处理改题参数；不引入超出年级的新概念，也不能挤占主问题的讲解焦点。

开发前的教学方案必须明确写出：目标年级、认知边界、核心卡点、可观察证据、主推理链、反向验证和拓展思考。缺少其中任何一项时，不进入编码。

## 参数动态规则

题目中的所有数字都必须来自参数或计算结果，不能写死默认题目的数字和结论。

正确做法是固定讲题节奏，动态生成讲题内容。

例如租车问题不能写死：

```text
8 辆大车 + 2 辆小车 = 6760 元
```

而应该根据参数动态计算：

```text
总人数 = 老师人数 + 学生人数
全大车方案 = ceil(总人数 / 大车座位)
全小车方案 = ceil(总人数 / 小车座位)
每座价格 = 租金 / 座位数
所有可行搭配 = 枚举大小车组合
最优方案 = 可坐下且费用最低的方案
```

如果参数变化导致判断方向变化，讲解文案也必须变化。

例如：

- 大车每座更便宜：从大车优先的思路开始推演。
- 小车每座更便宜：从小车优先的思路开始推演。
- 两者每座价格相同：重点比较空座和总费用。

## 推荐代码结构

每个复杂应用题页面优先使用下面结构：

```js
function buildProblemState(params) {
  // 清洗参数，计算所有基础数据
}

function buildSlides(problemState) {
  // 根据当前参数动态生成讲题步骤
  return [
    { type: "problem-intro", fullProblem, givens, task, openingQuestion, visualData },
    { type: "analysis", title, lead, formula, visualData },
    { type: "trial", title, lead, formula, visualData },
    { type: "summary", title, lead, formula, visualData },
    { type: "answer", title, lead, formula, visualData }
  ];
}

function renderSlide(slide) {
  // 只渲染当前步骤
}
```

不要把默认题目的具体过程直接写进 DOM。默认题目只是一组初始参数。

## 效果设计方案模板

开发前先给用户确认下面内容：

```text
题目：
这里写完整题目。

Design Read：
写清受众、视觉方向、设计参考、Keep / Adapt / Avoid 和题目专属视觉。

可修改参数：
列出所有数字和单位。

页面布局：
说明单一主舞台如何承载完整推理，以及低强调工具放在哪里。若确实需要常驻控制区，说明为什么它不会分散注意力。

点击流程：
1. 第一步如何在讲题舞台内完整呈现题目情境、全部已知条件与单位、所求问题，以及让学生复述题意的开场提问；第一步不讲方法或局部推导。
2. 第二步显示什么画面、什么文字、什么公式。
3. ...

动态规则：
说明参数变化后，哪些步骤、判断、文案会跟着变。

答案揭示时机：
说明第几步才出现比较表，第几步才出现最终答案。

验证场景：
列出至少两个参数变化案例，确认讲解不会写死。

视觉验收：
说明如何确认项目设计系统、桌面布局、交互状态和数学视觉焦点；必须包含 `1366×768`、`1440×900` 两个桌面视口，以及开场页、内容最密集步骤和最终页三个状态。
```

用户确认后再开发。

## 视觉和交互要求

- 每一步只讲一个核心问题。
- 当前步骤的视觉变化要足够明显。
- 公式、图形、素材、讲解文字要同步变化。
- 数学舞台优先修改持久对象的状态，不因翻页整体重建并重播入场动画。
- 点击舞台空白处、“下一步”或键盘后只推进一个语义步骤，动作完成后停住。
- 算式在对应的数学动作之后揭示，并尽量靠近它所解释的对象。
- 参数修改后，讲解应回到第一步或保持在可理解的步骤，并重新生成内容。
- 不要在页面首屏堆满所有方案。
- 表格只用于后半段汇总，不作为第一屏主体。
- 如果使用人物、车辆、图形素材，素材应服务于推理，不只是装饰。
- 删除任何不能回答“它帮助学生看懂当前哪一个数学关系”的装饰、卡片、图标、动效或重复文字。
- 页面只面向电脑浏览器，不要求设计或验收平板、手机等窄屏布局。

## 视口与翻页控制硬性规则

- 在 `1366×768` 和 `1440×900`、浏览器缩放 `100%` 的桌面视口中，页面不能产生需要寻找主导航的纵向滚动；上一页、页码、下一页必须完整位于首屏内。
- 桌面端逐一检查开场页、内容最密集步骤和最终页，要求 `document.documentElement.scrollHeight <= window.innerHeight + 1`，并要求主导航按钮的 `getBoundingClientRect()` 完整落在视口内。
- 如果内容放不下，拆成更多讲解步骤，或减少非教学留白和装饰。不得缩小学生正文、裁切内容、给教学区增加内部滚动，或使用过大的固定 `min-height` 把主导航推到视口外。
- 推荐桌面课堂外壳使用 `height: 100dvh`、五行网格 `auto auto auto minmax(0, 1fr) auto`，并给工作区和舞台设置 `min-height: 0`；不能只写 `min-height: 100vh` 后让内容自然向下撑开。

## 验收清单

新增题目开发完成后，至少检查：

- 第一页在讲题舞台内完整呈现题目情境、全部条件和单位、所求问题，并且没有进入方法或局部推导，也没有提前显示最终答案。
- 点击下一步时，数学舞台的主体画面明显变化。
- 舞台空白处、“下一步”和键盘每次只推进一个步骤，动作结束后停止，不发生自动连播。
- 相邻步骤共享同一个舞台框架；不变对象不闪烁、不跳位、不重复入场。
- 每个步骤只有一个明显视觉焦点，没有侧栏、装饰或重复信息与它竞争。
- 每一步的公式和讲解对应当前画面。
- 修改任意参数后，推演内容重新计算。
- 至少测试一个会改变判断方向的参数案例。
- 最终答案只在最后一步出现。
- 比较表只在后半段出现。
- 素材图片加载正常。
- `1366×768` 和 `1440×900` 的开场页、内容最密集步骤、最终页都无需纵向滚动即可看到完整主导航。
- 两个目标桌面视口都没有重叠、裁切或横向溢出。
- 模型计算逻辑有测试覆盖。
- 页面符合已确认的 `Design Read` 和项目 `DESIGN.md`。
- 视觉层级首先突出当前数学问题，而不是装饰或品牌模仿。
- 所有主要控件具备清楚的悬停、按下、键盘焦点和禁用状态。

## 租车问题形成的经验

这次租车题的最终经验是：

- “最省钱”类题目不能直接展示最优答案。
- 应先展示纯方案，再比较单价，再提出混合方案，再汇总验证。
- “大车更划算”不是固定结论，必须由当前参数计算得出。
- 混合方案也不能写死，应动态选择最有代表性的候选方案。
- 讲题流程固定，数字和判断动态生成。
